# Audit remediation plan

Audit date: 2026-09-25. Complete each change and its focused regression checks before starting the next. No production deployment or live payment actions are part of this plan.

1. **Complete locally — Trusted Clerk authentication.** Key retrieval and issuer validation are pinned to `CLERK_ISSUER_URL` in a shared verifier. Missing/invalid configuration is rejected. Real-signature regression tests cover hostile issuers, wrong keys, expired/malformed tokens, and the admin allowlist. Environment examples, Render configuration, and deployment checks are updated. Validation: all 84 API tests pass (39 new auth cases), both workspaces pass typecheck, and `git diff --check` passes. **Deployment prerequisite:** set the trusted issuer on the host before deploying; live Clerk sign-in remains to be verified after deployment.
2. **Complete locally — Signed Stripe webhooks.** Uses the Stripe default export and registers the webhook route after the raw-body plugin is ready. Six HTTP integration tests use the installed SDK to sign original request bytes, cover payment/refund processing, and reject missing, wrong-secret, tampered, and expired signatures without order mutations. No live Stripe calls.
3. **Complete locally — Non-destructive seeding.** Product seeding uses insert-only `createMany` with duplicate skipping on both ID and slug. Adapter and actual PostgreSQL tests confirm preserved edits/depleted stock, missing products, renamed listings, and concurrent repeated seeding. Existing data already overwritten by earlier deployments must be restored separately from verified records/backups.
4. **Complete locally — Stock and listing enforcement.** Both stores reject unavailable listings/invalid quantities, aggregate duplicate lines, and reserve stock before checkout. PostgreSQL conditional updates and order creation run in one transaction. Reservations last 35 minutes and payment consumes them without a second stock deduction. Cancellation expires the Stripe session before releasing stock; expiration/failed-payment webhooks and startup/minute cleanup handle abandoned reservations. Saved requests and stable idempotency keys recover ambiguous creation failures; unrecorded sessions older than 23 hours require manual reconciliation. Regression checks cover request rejection/timeouts, delayed payments, expiry/races, concurrent buyers, whole-cart rollback, and repeated payment/cancellation. Migration `20260930010000_inventory_reservations` applied to isolated PostgreSQL 15. Legacy pending-session rollout policy is documented in `AUDIT_DEPLOYMENT.md`.
5. **Complete locally — Private order details.** Checkout issues a random 256-bit guest credential and stores only its SHA-256 hash. The frontend retains the credential in the checkout tab's session storage and uses an HTTP header after returning from Stripe; URLs do not contain credentials. Receipts require the guest credential, matching authenticated owner email, or admin authorization and return only receipt fields with caching disabled. Internal request data/hash are removed from account/admin responses. Tests cover absent/invalid/cross-order tokens, owners/admins, forbidden accounts, legacy receipts, disabled storage, and sign-in completion. Migration `20261001010000_private_receipts` applied to isolated PostgreSQL; historical guest links require account sign-in or support.
6. **Complete locally — Payment event state transitions.** Payment replays preserve later states and reject conflicting session/payment-intent identifiers. PostgreSQL rechecks the winning state after concurrent updates, including cancellation. Fulfillment requires a paid order and repeats safely for fulfilled orders. A transactional notification outbox, worker leases, fixed order snapshots, and per-recipient Resend idempotency keys handle payment replays and failed sends. Startup/minute processing retries deliveries within 23 hours; older ambiguous deliveries require manual reconciliation. Migration `20261001020000_payment_notifications` applied to isolated PostgreSQL. Payment sync verifies session ID, order metadata, completion status, and recorded payment intent; no-payment-required sessions require zero total. Signed HTTP tests cover delayed success, stale completion/failure/expiry after fulfillment, and payment after cancellation. Final invariant review and full workspace verification passed.
7. **Complete locally — Refund ledger and replay handling.** Both stores now calculate totals from individual refund IDs; PostgreSQL locks the order before reading/updating ledger rows and refund IDs are globally unique. Focused calculation tests cover A/B/A replay, pending-to-succeeded transitions, failure accounting, stale pending snapshots, changed amounts, and excess totals. Migration `20261001030000_refund_ledger` flags historical refund orders for reconciliation rather than trusting cumulative amounts. Migration applied successfully to isolated PostgreSQL. Real database tests cover concurrent A/B/A replay, global refund ownership, serialized current-state retrieval, notification uniqueness, and atomic historical reconciliation/rollback. Configured Stripe webhooks and admin refund results retrieve current snapshots under the order lock and verify payment ownership. Refund success/failure emails use transactional delivery jobs and stable keys. The admin-only historical reconciliation endpoint rebuilds the ledger from all Stripe refunds without emailing historical results. Provider mocks and signed HTTP tests cover stale events and ownership mismatches.

After all seven: run both workspace test suites, typecheck, and build; review migrations and deployment order. Record any remaining production-only validation separately from local test results.
